# Dynamic IPA decryption: evidence-led follow-up (2026-10-31)

Research branch: `feature/fairplay-runtime-ipa-import-20261031` (draft PR #32, based on draft PR #31).
Target: stock iPhone 16 Pro on iOS 27.0.1; install Crumb once, then import/download a personalized, licensed encrypted IPA at runtime, decrypt and export without Mac, jailbreak, JIT or per-target installation.

## Current hard facts

- The public FairPlayed proof of concept (Oct 29 commit `bad7df138839b5e0ac8b9f20cc4689140b8436fb`) works with an encrypted app included in the *installed* helper bundle. It explicitly says data-container copies fail System Policy and symlinks do not fix it. This is upstream-reported behavior, not a matched iPhone Crumb comparison for the exact same IPA.
- Crumb 23058 produced `mapping_attempted=true`, `mapping_errno=0`, `remap_attempted=true`, `remap_return=-1`, `remap_errno=12`, zero changed pages, and no matching authorized app-group container. This proves the syscall was attempted after a working `mmap`, but **not why** the FairPlay service refused it. The pinned 27.0.1 XNU errno branch converts many nonzero `text_crypter_create` returns into `ENOMEM=12`.
- The earlier 178 pages recovered from an *installed bundle* do not establish a same-IPA differential test against the later data-container failure. The safe report did not identify the app. No full exported IPA from an arbitrary runtime import has been verified.
- The CoreMedia CVE-2026-112706 published by MchinaMd57764 and forked by ceoca69 is a narrowly demonstrated **read/dir-list/existence** primitive, not an arbitrary writer. Its write request produced error `-12878` on iOS 26.5 and 27.0, and other apps' containers were refused. A CoreMedia read descriptor is not a per-file permission grant to `fairplayd`.
- A signed `Crumb.app` on a stock iPhone is not a mutable data directory. Putting files in `Documents`, `Library`, `tmp` or an authorized App Group does not turn them into original installed-bundle resources or grant another daemon access.

## New upstream research on 31 October

DrWhax/unfairplay **changed on 2026-10-31** with:
- `6317996cab1633e20843ec486df93da09567d1da`: pinned deterministic SIDB/SINF route, rejects fallback candidate scans, logs the selected private layout in private QA.
- `614457048fcfe6d2cd1831e9cf007faed025b505`: supports universal SUPP page tables.
- `5b0aa4896c7e67e226867a516eb1023182c512b4`: supports multiple declared SINF sources while rejecting ambiguous or mismatched replicas.
- `05f6c4d33caa23d0c792745ec60649a66a798377`: covers all mapped selection state slots.

This is a genuine algorithmic advance: the upstream `build.md` describes typed Go recovery, reducing reliance on pinned native instruction profiles. **It still starts from an enrolled Mac** with an installed matching app, private `SC Info` SIDB/SIDS files, matching SINF/SUPF, IOMACAddress, and related capture metadata. The reusable enrollment model is derived on that Mac. Independent Linux processing after enrollment does not prove an arbitrary iOS app can mint the same model.

Crumb has a different *mobile* input contract:
- `captureanalysis.go` recognizes `consumer-state.json`, retained `keybag.bin` and optional `diversitybag.bin`, and may observe `SC Info.sidb` generated by an **isolated StoreAgent/KBSync consumer**. It intentionally returns `portable_raw_state_verified=false`, `portable_enrollment_frame_verified=false` and `validated_portable_model=false` until the original SINF passes.
- `fairplaycapturebridge.go` refuses to treat a legacy capture as a modern enrollment. `fairplayenrollment.go` requires a differently structured `app/executable`, installed `app/SC_Info/` and `state/` evidence and hardware identity.
- `mobilelicense` has consumer-only 16-byte-credential support; it **does not produce** the legitimate credential on a stock iPhone.
- Previous mobile SINF check `-42057` remains an observed failure. Neither newly published Mac-only algorithm nor a new ZIP path can substitute for actual valid mobile enrollment state.

The expected useful upstream-port condition is **not** just that the phone has some bytes called `SC Info.sidb`. A private same-enrollment test must prove compatible state version/geometry, SINF selector and license association, correct device-derived input and complete authenticated SINF. Otherwise the Mac algorithm must fail closed.

## Security advisory triage

The official iOS 27.2 advisory dated 2026-10-26 establishes:
- `CVE-2026-112612` Accounts/trust pairing: arbitrary read/write requires physical access to a previously trust-paired device; outside the iPhone-only constraints.
- `CVE-2026-113896` FileProvider, `CVE-2026-112618` Files, `CVE-2026-113914` App Store and `CVE-2026-112628` **Shortcuts** are described as unauthorized sensitive-data access, not demonstrated bundle-write or FairPlay decryption.
- `CVE-2026-112576` kernel copy-on-write memory issue does not by itself establish persistent filesystem writes to a signed app bundle. No compatible, verified public technique was identified here.

*Correction*: the previous research note misidentified CVE-2026-112628 as Spotlight; the Apple advisory identifies **Shortcuts**. Corrected in `docs/IOS_27_2_CVE_ACCESS_RESEARCH_20261031.md`.

## Next falsifiable on-device experiment (no arbitrary file access)

**Matched input, same signed Crumb install, same Apple Account, same OS, identical IPA SHA256:**
1. An already signed test Crumb instance **containing an authorized test IPA as its original installed bundle resource** is the positive control; run the existing read-only native page-count validator.
2. From that same instance, use the existing runtime import mechanism to put an exact-byte copy of the same IPA and SINF beside its encrypted executable in Crumb's own data container. Run the same native reader. No output unless all pages verify.
3. Compare per-slice CPU type, crypt offset/size, SINF file presence/hash, `mmap`/remap attempted, native error, number of successfully read/changed pages. Do not publish paths, credential bytes or IPA contents.
4. The positive control must itself succeed to interpret the negative test: if both fail, investigate license/account mismatch or reader differences, not just sandbox policy. If installed succeeds and data fails with byte-identical input, the location/daemon-access hypothesis becomes much stronger.
5. Optional authorized App Group comparison is relevant only when Crumb's current signing entitlement and Foundation both confirm a dedicated group and it can be used without introducing another install. Do not fabricate an entitlement.

This first experiment needs one *known-good* authorized installed resource as a control and must not be represented as the desired final UX. It produces diagnostic evidence, not a runtime import workaround.

## Stop conditions and validation gates

- Do not implement CVE-112706 as arbitrary write; demonstrated write channel is denied.
- Do not relabel `ENOMEM` as "out of RAM" or "sandbox confirmed" from errno alone.
- Do not construct an unverified mobile credential from MAC address, DSID, SINF slices, decoded SIDB bytes or random trials.
- Do not publish partial/unauthenticated IPA results; all encrypted slices and pages must validate.
- Do not make users reinstall Crumb per IPA without acknowledging that this violates the requested workflow.
